# Query grammar

A search like `light mechs with at least 2 ppc and a srm6` is parsed by ANTLR into units and equipment chunks, then turned into SQL.

## Pipeline

1. `src/main/antlr4/me/Battletech.g4` is the grammar. `antlr4-maven-plugin` generates `me.BattletechLexer` / `me.BattletechParser` / `me.BattletechVisitor` during the build, so there's no generated code in git.
2. `antlr/QueryParser.parse(...)` runs the lexer and parser with a throwing error listener. Any syntax error fails the whole query with a `FailedParseException`, which the controller shows on the page. Never let ANTLR silently recover. `ThrowingErrorListener` turns ANTLR's raw messages into plain ones ("expected 'with' before 'at least'"), using the parser's expected-token set. When you add a token that users can leave out, add it to `describe` too.
3. `antlr/QueryVisitor` walks the tree:
   - `visitUnit` → `utils/UnitBuilder` maps the unit token's symbolic name to an entity class (`Mech`, `Vehicle`, `Vtol`, `Unit`) wrapped in a `UnitDecorator`. Body-plan words (`bipeds`, `quads`, `tripods`, `lams`, `quadvees`; user decision, 2026-10-30) are mechs with `UnitDecorator.locomotion` set (`AND locomotion = 'LAM'`). `omnimechs` / `omnimeks` / `omnis` are mechs with `omniFilter` true. The `omni` rule (`omni`, `non-omni` / `non omni` / `nonomni`) goes before or after the weight classes (`non-omni assault mechs`, `assault omni mechs`) and sets `omniFilter` for any unit word (`AND omni = true|false`).
   - **A unit alone is a whole query** (`lams`, `heavy omni mechs`). The `line` rule lists the unit-led alternatives before the bare `chunks` one on purpose: `lams` could also be read as a number-less chunk, and ANTLR resolves that ambiguity to the first alternative.
   - The words before the unit are the `weightClasses` rule: one or more weight classes joined by `or`, `and` or commas (`ultra light`, `medium or heavy mechs`, `light, medium, or heavy`; `and` means the same, since "light and medium mechs" asks for both). `UnitDecorator` filters `weight_class IN (...)`. A word there that isn't a weight class fails the search with "Unknown weight class: hevy" (user decision, 2026-11-01; before, it was left out, which searched every weight class). Suggesting the right spelling is planned as its own PR (autocorrect for every kind of term). After `or` with no weight class, the error says "expected a weight class" (`QueryParser.followsWeightClassOperator`). Commas (`COMMA`) are only allowed there; between equipment chunks they still fail to parse.
   - **Chunks become `model/UnitFilter`s** (component search, 2026-10-31). Each is a subquery of unit ids, a logical operator and a `negated` flag:
     - **Components:** `utils/ComponentNames` is checked first. It covers engine, armor, structure, gyro and cockpit types, built from the enums' texts plus the kind word (`xl engine`, `ferro-fibrous armor`, `small cockpit`, `command console`). Armor and structure also answer to the bare text when no other kind shares it (`endo steel`, `stealth`); `standard engine` = Fusion. A base type takes its prototype along (`endo steel` = `ENDO_STEEL` + `ENDO_STEEL_PROTOTYPE`). A tech word filters `engine_tech` / `armor_tech` / `structure_tech` (`clan xl engine`); gyros and cockpits have none, so a tech word there is an error. These become `model/ComponentFilter` (`SELECT id FROM unit WHERE engine_type IN (...)`). The quantity must mean one (`a`, `an`, `1`, `any`, `at least 1`); otherwise the error is "A unit has one engine: xl engines". `ComponentNamesTest` checks no component name is also an alias, family or shorthand key.
     - **`without`** (user decision: for weapons and components): `mechs without an xl engine`, `mechs without ppcs`, `... and without any lasers`. It can stand in for `with` right after the unit (`withoutChunks`). Equipment counts at least 1 and is negated (`id NOT IN (...)`). Its quantity may only mean one; otherwise the error is "'without' means none at all: use 'with fewer than 2 ppc'".
       - **The `negation` rule's words** (user decision, 2026-10-31): `WITHOUT` (`without`, `lacking`, `that don't have`, `that dont have`, `which do not have`), `NO` (`with no ppcs`, `but no lasers`, `mechs no ppcs`; `no more than` is the longer match and stays a comparator), and `EXCEPT` before a weapon (`but not lasers`). `BUT` is a logical operator meaning `and`. In the search box, swapping any of them offers `with`: right after a with-word (`with no ppcs`) the word is just taken out, anywhere else it becomes `with` (`mechs no ppcs` → `mechs with ppcs`; `without ppcs and no lasers` → `... and with lasers`, since taking `no` out would leave the lasers carried-over without).
       - **It carries over a list** (`QueryVisitor.Chunks`): the chunks after a negation stay negated while they have no number or a count meaning one (`a`, `an`, `1`, `any`, `at least 1`). Inside that run, `or` becomes `and`, so `without ppcs or lasers` = neither and `without an xl engine or a light engine` = neither. A chunk with its own count (`2 lrm 20`), an engine rating, or `with` again ends the run (`without ppcs or lasers but with 2 lrm 20`). With `without` written out each time, `or` stays `or`: `without ppcs or without lasers` = either. `with` may come again anywhere between chunks (`lead` / `more` take an optional `STOPWORD`), so a trailing `with` now errors as "expected a quantity after 'with'".
     - **Units left out** (user decision, 2026-10-31): `non-lam mechs` (`NONUNIT`, one token covering `non-` / `non ` / `non` plus a unit word; it has to be one token, or `non-lam` lexes as a `WORD`). Each unit word's spellings are a lexer fragment (`MECHWORD`, `VTOLWORD`, `HOVERCRAFTWORD`, ...) shared by its token and `NONUNIT`, so every spelling works after `non-` (`non-hover`, `non-helicopter`); add a new spelling to the fragment, not the token, `mechs except lams, quads and tripods`, `mechs that aren't omnis`, `units that are not vtols`, `mechs but not lams` (`exceptUnits`: `EXCEPT` and a list of unit words). Each excluded unit is built by `UnitBuilder` and becomes `AND NOT COALESCE((<its unitCondition>), false)`. The `COALESCE` is there because a vehicle's `locomotion` or a missing motive type is NULL. Before a weapon, `except` / `but not` mean `without` (`mechs except ppcs`).
     - **Engine rating:** `ratingChunk` (`RATING` token = `rating` / `rating of`): `an engine rating of at least 300`, `engine rating 300 or more`, `engine rating 300` (exactly) → `model/EngineRatingFilter`. The word before `rating` must be `engine` ("Can only search engine rating: ...").
     - **A chunk can leave out its number** (`chunks: lead more*`; `lead` = a chunk or a `bareChunk`), but only first or right after `and` / `or`: `mechs with endo steel`, `mechs with ppcs` (at least one), `2 ppc and endo steel`. Next to another chunk with no operator between them, the number is still required, so `2 ppc 3 srm6` still splits into two chunks. The operators sit between chunks in `more`, and the visitor sets each one on the filter before it.
     - Otherwise it's equipment: each `equipmentChunk` becomes an `EquipmentDecorator`. Its words are joined, lowercased, and looked up with `EquipmentRepository.findAllByNameOrSlang(name, lookup)`: equipment stored under the normalized name, plus every row the slang term with that key (`EquipmentNames.slangKey`, letters and digits) stands for. **Search reads only the database** (since 2026-10-30): MegaMek's other names (`ac 20` = `autocannon 20` = `ac/20`), families and shorthand are all slang terms. If nothing matches and the name ends in `s`, it tries the singular (`lrm 20s`). If several rows match (IS and Clan variants), the decorators are chained.
   - `EquipmentDecorator.buildComparison` + `model/search/QuantityConverter` turn the comparator token and quantity into a `Comparison` and an int.
4. `UnitDecorator.getQuery()` builds the SQL: a `dtype` / `weight_class` / `locomotion` / `omni` filter plus one `id IN (...)` (`id NOT IN (...)` when negated) subquery per filter, joined by each filter's `and`/`or` (default AND). **Tech is optional** (user decision, 2026-10-27, replacing the earlier per-variant counting): all matching equipment rows (IS, Clan, null tech) are counted together in one `equipment_id IN (...)` group, so "at least 4 medium laser" counts a mixed mech's IS and Clan lasers. A leading `clan` / `is` / `inner sphere` (`EquipmentNames.splitTechWord`, checked on the typed words before fire control: `clan artemis lrm 20`) keeps only rows of that tech. If the equipment exists but not in that tech (`clan plasma rifle`), the chunk matches no units (`EquipmentDecorator.matchesNothing`) instead of failing to parse; only names that don't exist at all give "Unable to parse".
- **Slang tables** (user decision, 2026-10-30: one term → many equipment rows, loaded by the importer after the units; `V3_6`):
  - `slang`: one row per term. `term` as written (`gauss rifles`), `lookup` (unique; `slangKey` of the term), `kind` (`model/SlangKind`).
  - `slang_equipment`: the equipment rows a term stands for. **Tech comes from the rows**: `lrms` links IS and Clan LRMs, MegaMek's `cllrm20` only the Clan LRM 20 (so `cllrm20s` is Clan only, and `is cllrm20` matches nothing).
  - Kinds: `ALIAS` (MegaMek names, `megamek/equipment-aliases.tsv`), `FAMILY` (an equipment group, the `equipment_group` tables; the term names the group and links no rows), `FAMILY_SINGULAR` (`atm`, unless stored equipment already has that name: `ppc` stays the PPC), `SHORTHAND` (hand-written: `jj`, `medevac`, `c3 master`, `escape pod`...; in the database since `db/data/V3_19`), `USER` (`POST /actuator/slang`). Terms only exist for stored equipment (links are by id). `utils/SlangTerms` builds the `ALIAS` and `FAMILY` kinds and `services/SlangLoader` saves them after each import; the hand-written kinds (`SHORTHAND`, `USER`) are stored, never rebuilt, and keep their keys: a group whose name is a hand-written term gets no term and is reported (`GROUP_TERM_TAKEN`, user 2026-11-13).
  - `ambiguous_slang`: keys MegaMek uses for two different items, kept for someone to decide (importers skill, bug 21).

## Gotchas

- **Lexer rules are tried longest match first, then by order in the file.** Keyword tokens (`MECH`, `ATLEAST`, `WITH`, `AND`, ...) must stay above `WORD`, or `WORD` swallows them.
- Multi-word tokens (`at least`, `or fewer`, `that have`) put the `GAP` fragment between their words: any number of spaces or tabs, so `at   least` works (user decision, 2026-10-29). Use `GAP`, not a literal `[ ]`, in new ones. A line break still splits them. `WHITESPACE` is skipped between tokens, not inside them.
- `NEWLINE` used to be `[\r\n]`-ish letters and matched the words `r` and `n`. It's now `('\r'? '\n' | '\r')+`. Test single-letter input when touching it.
- Case-insensitivity comes from the letter fragments (`M : ('M'|'m')`). Plurals come from a trailing `S*`.
- `QUANTITY` includes `a`, `an` and `any`, so none of them can be used as an equipment word. `any` means at least one whatever comparator is in front (`any lasers`, `EquipmentDecorator.buildComparison`), like `multiple` means more than one.
- `STOPWORD` is the word between the unit and the weapons: `with`, `having`, `that have`, `which have`, `carrying`, `armed with` (user decision, 2026-10-29). They all mean the same. `QueryVocabulary.WITH_WORDS` lists them for the search box, which offers them in place of each other; add new ones to both.
- Equipment names are the `equipmentName` rule: words plus an optional trailing `QUANTITY`. **The words can include unit tokens** (2026-10-31): after a number or `without` a unit word can't mean anything else, so `1 vehicle flamer`, `1 vtol jet booster` and `a superheavy tripod cockpit` work. The unit tokens are listed in the rule itself, not in a sub-rule, because `query-analysis.js` reads the name's words as direct children. A number-less chunk's name is `bareName`, which must start with a plain `WORD`. Otherwise `mechs at least 2 ppc` would read `mechs` as a name instead of missing its `with`, and `medium or mechs` as two names. The words (plus an optional trailing number) are joined with spaces (`visitEquipmentName`) and then normalized with `utils/EquipmentNames.normalize` (lowercase, no spaces, mounting notes like `(R)` / `(OS)` removed). The same normalizer is used on import and for slang, so `large laser` = `largelaser` and `lrm 20` = `lrm20`.
- **Fire control prefixes.** `artemis lrm 20`, `artemis iv srm 6`, `artemis v lrm 15` and `apollo mrm 40` search for launchers with that fire control. `FireControl.fromSearch` splits the prefix off the normalized name; plain `artemis` means IV or V. `EquipmentDecorator` adds `AND fire_control IN (...)` (enum names). Without a prefix, `lrm 20` counts every LRM 20, with or without Artemis. Fire control is stored on the launcher (importers skill, bug 20).
- **A trailing number is part of the name only if no word follows it.** A number lexes as `QUANTITY` whether it's `20` in `lrm 20` or the quantity of the next chunk. Because the name allows at most one trailing `QUANTITY`, and a chunk needs a word after its quantity, ANTLR's lookahead splits `mechs with 2 ppc 3 srm6` into `ppc` + `3 srm6`, but keeps `2 lrm 20 3 srm 6` as `lrm 20` + `3 srm 6`. Side effects: a name can't have a number in the middle (`lrm 20 artemis` reads as `lrm` with a chunk `20 artemis`), and `mechs with 2 ppc 3` asks for equipment `ppc 3` ("Unable to parse: ppc 3"). Tests: `QueryVisitorTest.equipmentNamesCanEndInANumber`, `aNumberBeforeAWordStartsTheNextChunk`.
- `tank` means every ground vehicle (dtype `Tank`, not VTOLs). `tracked` / `wheeled` / `hovercraft` are motive types; see the `vehicle-motive-types` skill.
- Unit and weight class SQL is built from enums. Equipment is matched by id after a repository lookup. Keep user text out of the SQL string.


## The search box (browser side)

The search box colors the query as you type and offers swaps on hover. It parses **in the browser** with JavaScript generated from the same grammar: a second `antlr4-maven-plugin` execution (`-Dlanguage=JavaScript`) writes `BattletechLexer.js` / `BattletechParser.js` to `target/classes/static/js/grammar/me/`, served as `/js/grammar/me/...`. The ANTLR runtime is vendored at `static/vendor/antlr4/antlr4.web.js` (antlr4@4.13.2 `dist/antlr4.web.mjs`, renamed `.js` so it's served as JavaScript; module scripts need a JavaScript MIME type). It **must stay the same version as `antlr4.version`** in the pom. The import map in `templates/fragments/search-form.html` points the generated code's bare `antlr4` import at it.

- `static/js/query-analysis.js` (no DOM): `analyze` gives each word a role from the parse tree; `alternatives` lists swaps; `replaceToken` applies one. **It splits equipment names the same way `QueryVisitor` does** (tech word, then fire control, then the name). Change both together.
- `static/js/query-input.js`: replaces each `<input data-query-input>` with a contenteditable field and keeps the hidden input in sync, so the form submits unchanged. Without JavaScript, the plain input still works.
- **Templates** (user decision, 2026-10-28): the "+ unit" and "+ weapon" buttons add a section of blanks, written into the query as `<weight class> <unit> with <comparator> <quantity> <weapon>` (`TEMPLATES` in query-analysis.js); a weapon section after another starts with an `<and/or>` blank. Each blank's list opens in turn (guided fill-in; a number, blank or typed, gets a box to type it in instead of a list: `isQuantity`, `quantityText`), and the search runs once the last is filled. Typing in a blank replaces it. Escape, or searching early, fills the rest with `SLOT_DEFAULTS` (`fillSlots`, also run on submit), so **the server never sees a blank**. `analyze` reads a query with blanks by padding each default to the blank's length, which keeps offsets, so every default must fit in its blank. Equipment dropdowns also offer adding a tech (`clan only`, inserted before any fire control) and, for LRM/SRM/MML (not Streak) and MRM families, `with artemis` / `with apollo`.
- **Word lists:** `GET /api/vocabulary` (`web/VocabularyController`) serves `antlr/QueryVocabulary`: weight classes (`WeightClass`), unit words and comparators (`QueryVocabularyTest` checks each still lexes to the right token), tech words (`EquipmentNames.techWords`), fire controls (`FireControl.searchWords`, which `fromSearch` also reads), and equipment families. It lists only family weapons that some unit has and a query can type (`QueryVocabulary.isTypeable` runs them through the real parser). A weapon whose name can't be typed is listed under a spelling that can (`QueryVocabulary.typedName`): `blazer` for the Binary Laser (Blazer) Cannon (user decision: binary lasers are just "blazers") and `vehicle flamer` for Flamer (Vehicle). It also serves `omniWords` and `components` (kind → `ComponentNames.names()`). In the box, a component offers the other types of its kind, `omni` offers `non-omni`, and `without` offers `with`. The new roles are `omni`, `without` and `rating` (`main.css` `.tok-*`).
- **Not mirrored yet:** fire control run into the weapon name in one word (`artemisivlrm20`). The server accepts it (`FireControl.fromSearch` works on the normalized name), but `query-analysis.js` only splits fire control at word boundaries, so the box colors it all as equipment with no dropdown (Copilot review, 2026-10-29; left as minor).
- **Equipment groups are slang terms** (user decisions 2026-10-29 and 2026-11-01): a hand-written tree in the database (user, 2026-11-12): `equipment_group` (name, `section` WEAPONS or EQUIPMENT for top groups, `position` for the guide's order), `equipment_group_parent` and `equipment_group_member` (equipment ids, every tech its own row), from `V3_16` and `V3_17`; `utils/EquipmentGroups` loads it. A search can name any level: `missiles` > `lrms` > `standard lrms` / `enhanced lrms` / `extended lrms` / `improved lrms` / `streak lrms`; `energy weapons` > `lasers` > `standard lasers` (> `er lasers`), `pulse lasers` (> `er pulse lasers`, `x-pulse lasers`, `vsp lasers`), `heavy lasers`, ... (user, 2026-11-01: ER lasers are standard lasers, X-pulse and VSP are pulse lasers, and ER pulse lasers have their own group under pulse); `ballistic weapons` > `autocannons` > `lb-x acs`, `ultra acs`, ...; `artillery`; `physical weapons` (> `vibroblades`, `industrial tools`: backhoe, chainsaw, mining drill, ...), `ams` (AMS, Laser AMS, RISC APDS), `pods` (A-, B- and M-Pods); also `narcs` under missiles, `tags` under energy weapons, `mg arrays` under ballistic weapons. Outside the weapons, `ammo` (every name with "Ammo", plus Narc / iNarc pods) and `ecm` (ECM suites and what has ECM built in: CEWS, EW equipment) are groups too (user, 2026-11-01), and so are `probes` (with the Watchdog and Nova CEWS), `c3` (> `c3i`: Improved C3 and the Nova CEWS), `jump jets` (with jump boosters, partial wings and UMUs), `case`, `myomers`, `speed boosters`, `stealth systems`, `heat`, `shields`, `industrial equipment` (hoists, trailer hitches, ...: not weapons), `chassis mods`, `drones`, `cargo`, `medical`. All top groups with section `EQUIPMENT`: the search guide's equipment section ("Other equipment"), and there's no `equipment` group (the user: "Equipment shouldn't be a group. It was a separate section on the page"). `EquipmentGroups.top()` is the weapon top groups, `equipmentTop()` these. The user uses the guide to check the data (2026-11-01: "I want to use that page to validate information"). A group is its own items plus everything in the groups under it, and a group can have two parents (`streak lrms` is under `lrms` and `streaks`). Each group with something stored under it is one `FAMILY` term pointing at the group (`slang.equipment_group_id`); `EquipmentRepository.findAllByNameOrSlang` finds its items with a recursive query down `equipment_group_parent` (native SQL, the typed word a bind parameter; about 0.4 ms), and they're counted together (`at least 4 lasers`, `at least 3 missiles`). **`lrms` covers every LRM type** (user, 2026-11-01). The singular works too (`1 atm`, `2 laser`, `1 missile`, a `FAMILY_SINGULAR` term) for groups ending in `s`, but only when no weapon has that name: `ppc`, `flamer`, `machine gun` and `gauss rifle` stay the single weapon. Tech and fire control still apply (`clan missiles`, `artemis lrms`). Laser subgroups go by type, not size: `medium lasers` is the plural of `Medium Laser`. Prototypes are in their base group (`Prototype ER Medium Laser (CP)` is an er laser). A group term beats a MegaMek name or shorthand spelled the same (user, 2026-11-01: `ams` is every anti-missile system, `c3i` includes the Nova CEWS; also `case`, `cargo`, `vibroblades`), but not `USER` slang. `EquipmentGroupsTest` reads the `V3_17` seed (test `GroupSeed`) and checks the tree hangs together, every term can be typed, and the test database's copy of the items (`src/test/resources/db/equipment-group-members.sql`: tests import their fixtures after the migrations, so `SearchFixtures.putEquipmentInGroups` adds them) matches the migration. `EquipmentGroups` refuses loops, unknown parents and a top group without a section. **To add or change a group:** a migration that writes the rows (and the same items in the test file), then a slang reload or a `db/data` migration for the terms, like `V3_18__equipment_group_slang.sql`. New techs of grouped items join their groups on import (importers skill, bug 21).
- **The search box only knows the groups right under a top group** (`EquipmentGroups.familyLevel()`: `lrms`, `srms`, `streaks`, `lasers`, `ppcs`, `autocannons`, ...), which it treats the way it treated the weapon families. `missiles`, `standard lrms` and the other levels get no dropdown yet: the user isn't sure how the dropdown should show a hierarchy (2026-11-01), so decide that before changing `VocabularyController` or `query-analysis.js`.
- **Tests:** `src/test/js/*.test.mjs` run with Node's test runner in Maven's `test` phase. `frontend-maven-plugin` installs Node into `target/node`, and the tests import from `target/classes`. When the grammar changes, check the JS tests too.
- **The search guide** (`/equipment`, "Search guide" in the header; `web/EquipmentController`, `templates/equipment.html`) explains each part of a query. Its word lists come from `QueryVocabulary` and the family slang, but the prose, the unit word meanings and the examples are hand-written: **when the grammar changes, update the guide.** `EquipmentControllerTest` checks every `QueryVocabulary` word is on it and runs every example (cells with `class="guide-example"`, and the example links) through `QueryParser`.
- **The equipment list** (bottom of the guide; `EquipmentService.equipmentTree`, rows from `equipmentWithSlang`): the group tree as nested `<details>` (`templates/fragments/equipment-tree.html`; top groups open, each with its item count), each item under every group whose own pattern matches it, then "Other equipment" for items in no group. One row per display name (IS and Clan rows together) with its techs, slang (shorthand, user terms; group terms are left to the tree) and other names (MegaMek aliases), as the user chose on 2026-10-31. A term is left out when its slang key, after `EquipmentNames.stripTechPrefix`, is the item's own name or a term already shown (`CLLRM20`, `IS LRM 20`). `static/js/equipment-filter.js` filters the rows as you type, matching each row's text plus the terms of the groups it's under (`lrms` keeps every LRM), hides groups left empty and opens the ones with a match.

## Adding things

- **Comparator:** add the phrase to the matching token in the grammar (`ATLEAST`, `NOMORE`, `EQUAL`, `LESSTHANCOMPARATOR`, `GREATERTHANCOMPARATOR`), or add a new token to the `comparator` rule and handle its symbolic name in `EquipmentDecorator.buildComparison`.
- **Quantity word:** add a `fragment` to `NUMBER` in the grammar and the word to `QuantityConverter.NUMBER_WORDS`.
- **Unit type:** add a token, list it in the `unit` rule, and map its symbolic name in `UnitBuilder` and `UnitDecorator.getQuery`.
- **Anything people type** (comparator, unit word, tech or fire control word): also add it to `QueryVocabulary` (or where it reads from) so the search box offers it.
- **Slang for everyone:** a `db/data` migration that adds `SHORTHAND` terms, written like `V3_19__shorthand_slang.sql` (moved there from `megamek/equipment-slang.tsv`, user 2026-11-13: the database is the source of truth): insert each term where its lookup is free, link it to stored equipment by name where the link is missing, and delete terms left with no link, so it can run again. A term can link several items (`machine gun ammo` = the full and half tons; `medevac` = MASH and paramedic equipment, counted together by rows: a MASH with 11 theaters counts 1). Slang loads keep it, and it settles an `ambiguous_slang` key. When an import stores a new tech of an item, `UnitService.addEquipment` links it to the hand-written terms its other techs have (`NEW_EQUIPMENT_SLANG`). Tests skip `db/data`, so `SearchFixtures.addShorthand` runs `V3_19` after the fixture imports. **Not kept:** a term whose item no unit has (`pulse laser rifle`, a battle armor and infantry item): add it with a migration or `POST /actuator/slang` once one is stored.
- **Slang for this database only:** `POST localhost:8081/actuator/slang` with `{"equipmentName": "medium laser", "terms": "ml, medium l"}` (`admin/SlangEndpoint`, admin port, localhost only) adds `USER` terms, which slang loads keep. Terms are one comma-separated string, because Actuator only binds string values from the JSON body. The equipment is found the way a search finds it; a name no stored equipment has is refused (400). An existing term becomes `USER` and keeps what it stood for. **Slang never carries a tech** (user decision, 2026-10-28): a leading `clan` / `is` / `inner sphere` is stripped from terms (`EquipmentNames.splitTechWord`), and the term links every tech of the equipment, even when the name has a tech (`ER PPC [Clan]`). Tech is only a search filter: `clan big ppc` looks up `bigppc` and keeps the Clan rows.
- Tests: `QueryVisitorTest` (parser only, mocked repository) and `SearchServiceTest` (fixture units via Testcontainers and `SearchFixtures`). Add both.

## Planned, not built

- **Group terms that are also a weapon's plural** (settled 2026-11-01: the user chose "group wins", so this stays as it is). Kept for the numbers: A family term is looked up before the plural fallback, so the plural of a weapon whose name is the family's singular searches the whole family: `2 ppcs` is every PPC (ER, heavy, light, snub-nose, ...), while `2 ppc` is the PPC alone. Full data: `mechs with 2 ppcs` 369 vs `2 ppc` 63; `2 gauss rifles` 128 vs 52; `units with 2 machine guns` 292 vs 260; `units with 2 flamers` 58 vs 33. Those four are all of them: the other families (`lasers`, `lrms`, `srms`, `streaks`, `torpedoes`, `mmls`, `mrms`, `atms`, `autocannons`) have no weapon with the singular name, which is why they also have a FAMILY_SINGULAR term. Options: rename the four families (`ppc family`, `any ppcs`, `all ppcs`), or make the plural mean the weapon and keep the family under another term. The search guide notes it under Equipment > Name; update it with the fix.
- **Unit words at the start of a number-less name** (left over from the 2026-10-29 item, mostly fixed 2026-10-31). Names may now contain unit words after a number or `without` (`1 vehicle flamer`, `1 mech mortar 1`, `1 vtol jet booster`). A chunk with no number still can't start with one (`mechs with vehicle flamers`; `bareName` starts with a `WORD`), so it needs `any`. The search box adds it: a swap for a number-less name that would start with a unit word gets `any ` in front (`small cockpit` → `any tripod cockpit`, `flamers` → `any vehicle flamer`; `startingAChunk` in `query-analysis.js`, checked with the lexer). Taking out a word in front of such a name does the same (`orAny`): "any tech" on `with is vehicle flamer` and "with" on `without vehicle flamer` or `with no vehicle flamer` all give `with any vehicle flamer`. The apostrophe in `'Mech Mortar` still fails to lex.
- **BAR armor as a rating** (user decision, 2026-10-31; build it when support vehicles are imported, importers skill bug 13). BAR (Barrier Armor Rating, 2 to 10) is a number, so search it like the engine rating: `with a bar rating of at least 7`, and `with bar armor` for any BAR. Until then `ComponentNames` leaves the `BAR_*` armor types out, so the guide and the armor dropdown don't offer them: `bar 2 armor` can't parse (a number mid-name), and no imported unit has BAR armor (it's on 229 vehicle files at the pinned commit, nearly all support vehicles, plus a few IndustrialMechs). `ComponentNamesTest.everyNameCanBeTyped` checks every offered component name parses.
- **Number words inside equipment names** (future work, 2026-10-29): `single`, `double` and `triple` lex as quantities, so `double heat sink`, `single heat sink` and `triple strength myomer` can't be typed. Heat sinks are searched through their own unit column and no TSM is stored as equipment today, so nothing breaks yet; it will once TSM is imported as equipment. Same fix shape as unit words: let `equipmentName` take these tokens after the quantity.
- **Era search.** The `unit.era` column exists. `Unit.getQuery()` (unused; `UnitDecorator` overrides it) sketches an era filter. It still refers to an old `mechs` table. `Battletech.g4` has a commented-out list of eras (Age of War ... IlClan) and a commented-out `WEIGHTCLASS` token.
- **Location filters** (the user wants these eventually: "CASE in the left torso", "jump jets in the legs"). `EquipmentDecorator.getQuery` has a placeholder. Since 2026-11-11 each item's `unit_equipment.location` is right (importers skill, bug 8), with one limit: an item in several locations (TSM, a split Heavy Gauss) stores only its main one (bug 30, with the table design that would fix it).
- **Synonym graph.** The old `SearchParameters` class noted that unit words form a graph (`vee` → vehicle, `tracked` is a vehicle) rather than a flat map. The old `LanguageMapping` class planned a hard-coded slang map (`LL` → Large Laser, `Vee` → Vehicle, `VSP` → Variable Speed Pulse). The `equipment_slang` table replaced that for equipment.

# Importers

Unit data comes from MegaMek files. `utils/ReadMegaMek` parses them, and `services/UnitService.persistUnits` saves them. `utils/ReadPDF` is an unfinished importer for the recognition guide PDF.

## Data source

MegaMek moved its unit files out of the main `megamek` repo (which now only has test fixtures) into **`MegaMek/mm-data`**. The `mm-data` tags lag far behind (latest `v0.3.1`, Jan 2026), so pin to a commit.

- Local checkout: `C:\Users\adam\workspace\mm-data`. It's a sparse, shallow, blobless clone with only `data/mekfiles/meks` and `data/mekfiles/vehicles`. Re-create it with:
  ```
  git clone --filter=blob:none --sparse --depth 1 https://github.com/MegaMek/mm-data.git mm-data
  cd mm-data && git sparse-checkout set data/mekfiles/meks data/mekfiles/vehicles
  ```
- Pinned commit: `d195e171b3c87801c8dbc5ffcb5f763e5da57483` (2026-10-27, matching MegaMek release v0.51.00.2).
- Point the importer at it: `MEGAMEK_MECHS_PATH=.../mm-data/data/mekfiles/meks`, `MEGAMEK_VEHICLES_PATH=.../mm-data/data/mekfiles/vehicles`.
- Counts at that commit vs the baseline dump:

  - `.blk` files: 1,453, vs 1,032 vehicles.

  - `motion_type`: Tracked 572, Hover 328, Wheeled 314, VTOL 155, WiGE 36, Submarine 15, Naval 9, Aerodyne 9, Rail 8, Hydrofoil 7.

### Format changes since the importer was written
- **MTF files no longer start with name/model lines.** They open with a `#` license comment block, then key/value lines: `uuid:`, `generator:`, `chassis:`, `model:`, `mul id:`, `Config:`, `techbase:`, `era:`, `source:`, `published:`, `rules level:`, `role:`, `quirk:`... **Fixed:** `ReadMechMTF` now skips `#` lines and reads fields by key (`readMtfFields`).
- **MTF weapon lines have no `IS`/`CL` prefix and no quantity** (`Medium Laser, Left Arm`; all 22,369 lines at the pinned commit). Each weapon now takes the unit's tech in `persistUnits`. For mixed-tech mechs the per-weapon tech is only in the critical slot listings (`CLERMediumLaser` vs `Large Laser`), so getting it right means reading the slots (bug 6). Rear-facing `(R)` also only appears in the slots. A few names contain `, ` themselves (`Rifle (Cannon, Heavy), Left Torso`); the location is after the last `, `.
- **`era:` is now a year** (e.g. `2755`), not an era name. The column is a string, so map years to era names or store the year. Decide before building era search; see the `query-grammar` skill.
- **Stable ids now exist.** MTF has `uuid:` and `mul id:` (163 of 4,263 mechs have no `mul id:`). BLK has `<UUID>` and `<mul id:>` (`-1` when unknown; 10 of 1,453 vehicles). Use the MegaMek `uuid` as the upsert key instead of name + designation (bug 1). Consider storing `mul id` too, for Master Unit List links.
- BLK keeps the same `<tag>`/`</tag>` structure, and `readBlkAllParameters` already skips `#` lines. Note the key `<mul id:>` includes the colon. New tags: `<UUID>`, `<year>`, `<role>`. Empty values are written on one line (`<Model></Model>`, `<Right Equipment></Right Equipment>`); **fixed:** these now parse as empty values.
- BLK Inner Sphere equipment is no longer prefixed (`Machine Gun`, `IS Ammo AC/2`), while Clan equipment still is (`CLLightMG`, `Clan Streak SRM 4 Ammo`).

## How data gets into the database today

- **Units ship as a data migration** (user decision, 2026-10-30). `db/data/V3_8__megamek_units.sql` is a `pg_dump --data-only` of an empty database after both imports at the pinned commit (units, equipment, unit_equipment, slang; 11 MB). Flyway loads `classpath:db/migration` and `classpath:db/data` (`spring.flyway.locations`); the tests only load `db/migration` (`src/test/resources/config/application.properties`) and run on fixture units. The old frozen dump `db/migration/V2_0__baselineData.sql` (a 2020-2021 `pg_dump`, units without a `megamek_uuid`) still loads, because applied migrations can't change, but `V3_7__remove_baseline_units.sql` deletes those units, their equipment rows and equipment only they used, and then V3_8 loads the imported ones. It's a plain `COPY` (user decision): **a database that already has imported units fails on V3_8** (duplicate `megamek_uuid`), so drop or empty it first. Re-importing on top updates units in place.
- **Running an import.** With the app running and `MEGAMEK_MECHS_PATH` / `MEGAMEK_VEHICLES_PATH` set, `POST localhost:8081/actuator/import` with `{"source": "mechs"}` or `{"source": "vehicles"}` (`admin/ImportEndpoint`, admin port, localhost only). It returns `{"added", "updated", "skipped", "failed", "slangTerms", "problems"}`. Each file is saved in its own transaction. At the pinned commit, adding into an empty database: mechs 3 min 40 s (4,100 added, 163 without a MUL id), vehicles 54 s (1,208 added, 236 skipped), on 2026-10-30 after the component and slang work (about 90 s and 33 s before it). Running it again updates every unit and adds nothing. Updating is slower than adding: on the scratch database (2026-10-30) about 5 min for mechs and 75 s for vehicles, the same on a second vehicles run, so it isn't the one-time display-name fill. Updates weren't timed before the slang/display-name change, so it's unknown whether that made them slower; the slang load itself takes under a second.
- **Slang is loaded after the units** (user decision, 2026-10-30): `services/SlangLoader` runs at the end of every mechs or vehicles import, or on its own with `{"source": "slang"}` (e.g. after editing `equipment-slang.tsv`). It replaces every term except the ones added by hand (`USER`), from the three name files (bug 21), for the equipment that's stored. See the query-grammar skill for the tables. At the pinned commit: 2,251 terms, 2,993 term-equipment links, 0 ambiguous keys (all 9 settled in `equipment-slang.tsv`, 2026-10-30).
- **Display names.** `equipment.display_name` (`V3_6`) is MegaMek's name for showing people (`AC/20`, `LB 10-X AC`), whichever name the file used (`EquipmentNames.displayName`); names MegaMek doesn't list keep the file's spelling without prefix, tags and size (`Ammo LRM-20 Artemis-capable`). The readers keep the name as written on `Equipment.displayName` for this; `UnitService.save` turns it into the display name and fills it on stored rows that have none.
- **Configuration.** Paths come from `MEGAMEK_MECHS_PATH`, `MEGAMEK_VEHICLES_PATH` and `RECOGNITION_GUIDE_PDF` (`battletech.import.*` in `application.yml`).
- **Error handling and import problems** (2026-10-29, user decision: every misread must be logged before the database pass). A file that throws is logged with its stack trace ("Unable to import ...") and skipped; most parser bugs show up there as NPEs. Anything a reader can't read, or reads but drops, is reported to `utils/ImportProblems` with the file: logged as it's found (warnings for things to fix, info for known gaps and expected names) and counted per `ImportProblems.Kind`. Each import ends with an "Imported ...: N added ... Problems:" line listing every kind with its count and a few examples, and the admin import returns the counts as `problems`. Warning kinds: unknown location, unknown mech config, unknown tech base, unknown heat sink type, unknown motion_type, unread `.blk` equipment section, Artemis/Apollo without a launcher, invalid uuid, failed file. Info kinds: no MUL id, unsupported unit type, size not kept (drones, MASH), equipment name missing from the alias table (once per name), ambiguous slang keys (counted by the slang load). **When adding a reader feature that can drop data, report it here.**
- **Tests.** `ReadMegaMekTest` parses real files copied from mm-data into `src/test/resources/megamek/` (5 mechs, 6 vehicles). Add a test there with each bug fix. `ReadMegaMekAllFilesTest` parses every file in the checkout, but only when `MEGAMEK_MECHS_PATH` / `MEGAMEK_VEHICLES_PATH` are set, and **fails on any warning**, so a new kind of misread shows up there; it prints the summary, info kinds included. At the pinned commit: 4,263 mechs and 1,453 vehicles, 0 failures, 236 vehicles skipped (bug 13), 0 warnings (after bug 19 and the vehicle sections fix, 2026-10-29). Info: 163 + 10 without a MUL id, 236 skipped vehicle types, 13 drone / MASH sizes. Tests that search need units: `SearchFixtures` (test config) imports `src/test/resources/megamek/{meks,vehicles}` plus units picked for the search tests in `megamek/search/`, slang included; tests that `@Import` it get their own database.

## Known bugs

All of these were checked against the code. The "Data:" lines are from the baseline database.

### Both formats
1. ~~Re-importing duplicates units.~~ **Fixed:** `V3_0__unit_megamek_ids.sql` adds `unit.megamek_uuid` (unique) and `unit.mul_id` (not unique). `UnitService.save` finds the stored unit by MegaMek uuid, keeps its database id, swaps in the new equipment and deletes the old equipment rows. Every file at the pinned commit has a unique uuid. MUL ids group variants: the user decided that units sharing a MUL id are variants of the same unit. 163 mechs and 10 vehicles have no MUL id (MegaMek's own units), and 11 MUL ids are shared. `UnitRepository.findByMulId` returns a unit's variants. Verified on a scratch database with a full import run twice: same unit, equipment and unit_equipment counts, and no orphaned rows. Data: the baseline has 11 name/designation pairs that appear twice.
2. ~~Equipment names are flattened.~~ **Fixed:** `utils/EquipmentNames.normalize` (lowercase, no spaces, mounting notes removed) is used on import, for search words and for slang, so `medium laser` matches `mediumlaser`. Numbers after a space (`lrm 20`) still don't parse; see the query-grammar skill.
3. ~~Annotations stay in equipment names.~~ **Fixed for mounting notes:** `(R)`, `(OS)`, `(I-OS)`, `(iOS)` and `(ST)` are stripped by the normalizer. Annotations that name a different item (`(Vehicle)`, `(B-Pods)`, `(Blazer)`, `(Cannon, Heavy)`) are kept.
4. ~~Missing tech gives a third copy of the equipment.~~ **Fixed in the parsers:** every unit and every piece of equipment now gets a tech (0 nulls across the pinned commit), via `Tech.fromTechBase` / `Tech.chassisTech`.
25. **Only units in the Master Unit List are imported** (user decision, 2026-10-28: the MUL is the official list). `UnitService.persistUnits` refuses a unit without a MUL id: it's logged ("has no MUL id") and counted as `failed`. At the pinned commit that's 163 of 4,263 mechs (mostly 3025 CCE, Shrapnel, Videogame (Apocryphal), Force Manuals, XTRs) and 10 of 1,453 vehicles. Readers still parse those files, so parser tests can use them (the Goliath GOL-1M and Hybrid Rifleman fixtures have none). Imports still match on `megamek_uuid`; `mul_id` isn't unique (variants share one).
26. **Mixed-tech mechs with both versions of a weapon in one location get one tech for all of them.** `slotTech` gives every weapon in a location the tech of the first prefixed slot that matches. The Kodiak (Cale) (`Turning Points/JTP Dieron`) has 3 `CLERMediumLaser` and 2 `ISERMediumLaser` slots in the left arm, and all 5 become Clan. Its unprefixed IS weapons (Heavy PPC, AC/10) also become Clan, like bug 11's limitation on Clan-chassis vehicles. Not fixed yet.
19. ~~Some mech weapons have no location.~~ **Fixed (2026-10-29):** `Location` gained `FRONT_LEFT_LEG`, `FRONT_RIGHT_LEG`, `REAR_LEFT_LEG`, `REAR_RIGHT_LEG` (quads) and `CENTER_LEG` (tripods), and `Locomotion` gained `TRIPOD`, `LAM` and `QUADVEE` (from the first word of `Config:`). Before, 205 items had no location and 47 mechs no locomotion. Both columns are strings, so no migration. LAMs use biped locations.

27. **Sarna links land on disambiguation pages** (planned 2026-10-28 as its own PR; lowered to low priority 2026-10-29, user decision: do it after the other planned work). `LinkBuilder.buildSarnaUnitURI` guesses `sarna.net/wiki/<name>#<designation>`. That's only right when Sarna's title is the bare name. Shared names get a qualifier: the right pages are `Avalanche_(OmniMech)` and `Apollo_(BattleMech)`, and `Mad Cat` redirects to `Timber Wolf (Mad Cat)`. MegaMek files and the MUL carry no Sarna links. **Agreed plan:**
   - store the page per unit in a new `unit.sarna_page` column
   - fill it with an admin action on the localhost-only management port, never during the import, so imports don't depend on Sarna being up
   - the action uses Sarna's MediaWiki API (`https://www.sarna.net/w/api.php?action=query&format=json&redirects=1&titles=A|B|...`, up to 50 titles per request, slowly, with a user agent naming the project). For each chassis it tries the qualified title for the unit type first (`(BattleMech)`, `(OmniMech)`, `(IndustrialMech)`, `(Combat Vehicle)`, ...), then the bare name, following redirects
   - a hand-kept override file covers what that can't resolve
   - search results use `sarna_page` and fall back to today's guess

   Checked 2026-10-28:
   - the batch title query works
   - `prop=pageprops` / `prop=categories` return an internal API error on Sarna, so the API can't say whether a bare title is itself a disambiguation page (e.g. `Bulldog`); the override file is for those
   - `Atlas (BattleMech)` doesn't exist but `Atlas` does

### Mechs (`ReadMechMTF`, `.mtf`)
5. ~~Mixed-tech mechs get no tech.~~ **Fixed:** `Tech.fromTechBase` maps `Mixed (IS Chassis)` / `Mixed (Clan Chassis)` to `MIXED_TECH`. At the pinned commit: IS 2708, Clan 1178, Mixed 377.
6. ~~Per-weapon tech isn't read.~~ **Fixed:** weapon lines have no prefix, so `readMtfWeapons` looks for a slot in the same location named with a `CL` / `Clan ` / `IS` prefix that matches the weapon (letters and digits only, so `Ultra AC/10` = `CLUltraAC10`). If there's a match, that's the tech; otherwise it's the chassis tech. Mixed mechs' weapons come out 1,246 Clan and 802 IS.
7. ~~The fixed field order is fragile.~~ **Fixed:** fields are read by key. A missing required field throws an `IOException` naming the file and field.
8. **Armor isn't imported.** ~~Critical slot contents~~ **Partly fixed:** `readMtfSlotEquipment` imports ammo per slot (one ton each; 9,837 tons at the pinned commit) and equipment from an allow-list (`SLOT_EQUIPMENT`: targeting computer, CASE, TSM, MASC, ECM, probes, C3 slaves, melee weapons and others; 4,050 items), once per mech each. It's an allow-list because slots also repeat every weapon under different names (`LBXAC10` for `LB 10-X AC`), and those can't be told apart from equipment without MegaMek's equipment tables. C3 master computers are left out because some mechs also list them as weapons. Anything new in mm-data that's not on the list is silently skipped; run `SlotSurvey`-style checks (names that match no weapon in their location) when updating the pinned commit. Mech and vehicle ammo now share names (`IS Ammo LRM-20` and `IS Ammo LRM-20` both become `ammolrm-20`).
20. **Fire control (Artemis IV, Artemis V, Apollo) is part of the launcher, not equipment.** The user decided on 2026-10-27 that it's an attribute of the launcher: `UnitEquipment.fireControl` / `unit_equipment.fire_control` (`V3_2`), enum `model/FireControl`. MegaMek lists it as separate equipment right after its launcher: mech slots `SRM 6, SRM 6, ISArtemisIV`, vehicle lines `LRM 20` then `ISArtemisIV`. `attachMtfFireControl` / `convertToEquipment` put it on that launcher, or else on the first launcher in the same location it fits that has none yet. Artemis V fills two mech slots per system (`FireControl.getSlots`). Compatible launchers: LRM / SRM / MML / LRT / SRT, including improved and enhanced (not extended: no unit has that), for Artemis; MRM for Apollo. At the pinned commit every system attaches: mechs Artemis IV 386, Artemis V 58, Apollo 22; vehicles 129 / 10 / 2. **Artemis-capable ammo stays its own ammo type** (`ammosrm-6artemis-capable`), as the user decided. Search: `artemis lrm 20` (either Artemis), `artemis iv ...`, `artemis v ...`, `apollo mrm 40`; see the query-grammar skill.
21. **Mechs and vehicles name the same equipment differently.** ~~Not mapped.~~ **Fixed with an alias table:** `.mtf` weapon lines use MegaMek display names (`AC/20`, `LB 10-X AC`, `Machine Gun`), but `.blk` files and critical slots use internal / lookup names (`Autocannon/20`, `ISLBXAC10`, `MG`, `RL10`, `SRM2 IOS`). `src/main/resources/megamek/equipment-aliases.tsv` (alias<TAB>display name, 4,314 rows) is generated from MegaMek's source by `scripts/GenerateEquipmentAliases.java`, which reads `name =`, `setInternalName` and `addLookupName` in `common/weapons/**`, `MiscType` and `AmmoType`. `EquipmentNames.canonical` maps any of them (IS/CL/Clan prefix, `[Clan]` suffix and mounting notes removed; compared on letters and digits) to the normalized display name. The importer uses it (`UnitService.save`), since the equipment rows don't exist yet; search doesn't. **After each import the same files become slang terms in the database** (`utils/SlangTerms`, `services/SlangLoader`; user decision 2026-10-30): every MegaMek name of stored equipment is an `ALIAS` term linked to its rows (a tech prefix, `CLLRM20`, links only that tech's rows), each family a `FAMILY` term, and the hand-written `equipment-slang.tsv` lines `SHORTHAND` terms. Search reads only those tables. **A key MegaMek uses for two different items gets no term; it goes in `ambiguous_slang`** (one row per candidate) for someone to decide (user decision: never drop them silently), and is counted as `AMBIGUOUS_SLANG`. A line in `equipment-slang.tsv` (then `{"source": "slang"}`) or `POST /actuator/slang` settles one. A shorthand term can be on several lines to link several items; the importer names a unit file's item after the first line. At the pinned commit there were 9, all settled by the user (2026-10-30), mostly as "link both, the unit type sorts it out": `mechanical jump booster` = the mech and battle armor boosters (the mech version first, so mech files import as `Mech Mechanical Jump Boosters`; before this they stored the raw `mechanicaljumpbooster`); `machine gun ammo` and the light / heavy ones = the `[Full]` and `[Half]` tons (the plain MegaMek item is ProtoMech ammo); `ammo streak-5` / `clan ammo streak-5` = Streak LRM 5 ammo; `gauss rifle magshot` / `magshot gauss rifle` = the mech Magshot plus the battle armor and infantry guns; `pulse laser rifle` = the IS and Clan infantry items (nothing stored yet: battle armor and infantry aren't imported); `vibro sword` = those infantry blades plus every size of mech vibroblade, and `vibroblade(s)` = every size of mech vibroblade (the user asked for both). The old-spelling lookup (`equivalentNames`) is gone with the baseline. Artemis-capable ammo isn't in the table (MegaMek generates those variants in code), so it keeps its raw name on both sides. **To regenerate** for a new MegaMek version: sparse-clone `MegaMek/megamek` at the matching tag (`git clone --filter=blob:none --sparse --depth 1 --branch <tag> https://github.com/MegaMek/megamek.git megamek-src && cd megamek-src && git sparse-checkout set megamek/src/megamek/common`), then from this repo run `java scripts/GenerateEquipmentAliases.java <megamek-src>/megamek/src/megamek/common <tag>`. The local checkout is `workspace/megamek-src`, next to this repo (v0.51.00.2). The same script writes `equipment-family-slang.tsv` (family term<TAB>display name, 326 rows): weapon families from the folder MegaMek keeps each IS/Clan weapon in (`FAMILIES` in the script; e.g. `lrms` = `lrms/**` minus torpedoes, `ppcs` = `ppc/**` minus plasma weapons, `machine guns` minus MG arrays). Search and the search box use it through the `FAMILY` terms (query-grammar skill).

### Vehicles (`ReadVehicleBlk`, `.blk`)

## Regenerating data

The data is regenerated by running the import again: mechs, then vehicles (each reloads the slang). Units are matched on `megamek_uuid`, so a re-import updates in place. To ship new data to every database, add a new data migration in `db/data` (never edit `V3_8`): import into an empty scratch database whose Flyway skips `db/data` (`SPRING_FLYWAY_LOCATIONS=classpath:db/migration`), dump it the way `V3_8`'s header says, and write the next version as updates of what's stored, not a second full load (V3_8's rows are already there).

- Remove `\restrict` / `\unrestrict` lines (pg_dump 16.10+), `SET` lines and the `set_config('search_path', ...)` line from a dump: they're psql commands or would change the session for later migrations.
- Never edit `V1_0` / `V2_0` / `V3_8`; existing databases have already applied them.
- For a new mm-data commit: run `ReadMegaMekAllFilesTest` against it first (no warnings), then import into a scratch database and compare before replacing the real one.
- Compare counts per `dtype` and `tech`, distinct equipment names, names matching `[():]`, slang terms per kind and the `ambiguous_slang` rows. The search tests run on fixture units (`SearchFixtures`), not on the imported data.
